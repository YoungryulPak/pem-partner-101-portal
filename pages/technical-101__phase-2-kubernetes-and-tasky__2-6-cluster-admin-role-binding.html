2.6 cluster-admin role binding

Time 15 minutesAWS cost None beyond the running clusterNeeds 2.4 completedSource script Technical_Exercise/phase2_k8s_tasky/p2demo/214_ClusterAdminRole.sh; k8s/02_serviceaccount_rbac.yaml

Goal

Show that the application's service account is bound to the most powerful role in the cluster, and see what that allows, without exploiting it.

Why it matters

The application runs with a service account bound to the built-in cluster-admin role. Suppose the application is compromised. Then the attacker holds a token that can do anything in the cluster, including reading every Secret. An internet-facing workload with cluster-admin is a classic top-priority attack path. It is the Kubernetes version of the over-broad cloud role in 1.4 Over-permissive IAM role. The incident drill in 4.5 Attack simulation and incident response builds on this lab.

Before you start

Phase 1 is deployed. kubectl points at your cluster (see 2.1 Deploy EKS with Terraform). Run the commands from the phase2_k8s_tasky folder unless a step says otherwise.

The binding comes from k8s/02_serviceaccount_rbac.yaml:

kind: ClusterRoleBinding
metadata:
  name: tasky-cluster-admin-binding
subjects:
  - kind: ServiceAccount
    name: tasky-sa
    namespace: tasky
roleRef:
  kind: ClusterRole
  name: cluster-admin
kubectl apply -f k8s/02_serviceaccount_rbac.yaml

Steps

Step 1: confirm the binding exists

kubectl get clusterrolebindings -o json | jq -r \
  '.items[] | select(.subjects[]?.namespace=="tasky") | .metadata.name + " -> " + .roleRef.name'
PartMeaning
kubectl get clusterrolebindings -o jsonList cluster-wide role bindings as JSON
jq -r '...'Filter the JSON (jq must be installed)
select(.subjects[]?.namespace=="tasky")Keep bindings that involve the tasky namespace

Expected: tasky-cluster-admin-binding -> cluster-admin.

Step 2: see what cluster-admin grants

kubectl describe clusterrole cluster-admin

Expected: all verbs on all resources.

Step 3: ask the API what the service account can do

kubectl auth can-i --list --as=system:serviceaccount:tasky:tasky-sa
PartMeaning
kubectl auth can-i --listList what an identity may do
--as=system:serviceaccount:<namespace>:<name>Check as that service account

This is safe: it asks the API server and does not use or steal a token.

Expected: . [] [] [*], meaning every verb on every resource.

Verify

The binding exists (1), the role is all-powerful (2) and the API confirms the account can do everything (3).

Fix it

Give the application only what it needs. Most applications need no Kubernetes API access at all.

kubectl delete clusterrolebinding tasky-cluster-admin-binding

Then check again with Step 3: the list should be nearly empty. Remove the binding from 02_serviceaccount_rbac.yaml too, or kubectl apply will recreate it.

Troubleshooting

SymptomLikely causeFix
jq: command not foundjq not installedInstall jq, or read the output of kubectl get clusterrolebindings by eye
Step 1 prints nothingBinding not appliedApply the file above

Clean up

Remove the binding when you finish the labs (see 2.9 Destroy in the right order).

Check yourself

  1. Why does cluster-admin on an internet-facing pod matter?
  2. How does auth can-i avoid touching a real token?
