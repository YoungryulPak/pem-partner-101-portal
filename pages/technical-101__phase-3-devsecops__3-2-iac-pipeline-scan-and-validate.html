3.2 IaC pipeline: scan and validate

Time 25 minutesAWS cost None (GitHub Actions free minutes)Needs 3.1 completedSource script Technical_Exercise/phase3_devsecops/.github/workflows/iac-security-scan.yml; 320_CICD_Pipeline_IAC_Build_Push.sh

Goal

Run a pipeline that scans the Terraform code for misconfigurations on every change, before anything is deployed.

Why it matters

Infrastructure as code (IaC) lets you find a weakness in a file before it exists in the cloud. Scanners such as Checkov and tfsec read Terraform and flag problems like an open SSH port or a public bucket. This is the code-stage twin of the cloud findings you saw in Phase 1.

How the pipeline is built

PartWhat it does
TriggerA push to main or a pull request that touches phase1_vm_mongodb/ or phase2_k8s_tasky/terraform/
PermissionsRead the code; write security events (to upload results)
CheckovScans Terraform and writes results in SARIF format
tfsecA second scanner with its own rule set
Terraform validateChecks the code is well formed
UploadSends results to the GitHub Security tab

It does not run terraform apply. The Terraform state lives only on your machine. A GitHub runner cannot see it. Applying from the pipeline would first need the state moved to shared storage, such as an S3 backend with locking. So the pipeline only scans and validates. You apply the change locally yourself.

It does not block on findings. The lab is weak on purpose, so many Critical and High findings are expected. The scan is set to soft-fail. It shows the findings, but it lets the run pass anyway. This is a common first step in real programs. Make the problems visible first. Enforce the rule later.

Steps

Step 1: trigger a run with a small change

git checkout -b test-iac-scan
echo "# scan trigger" >> phase1_vm_mongodb/versions.tf
git add -A && git commit -m "Trigger IaC scan"
git push -u origin test-iac-scan

Open a pull request for the branch on GitHub.

CommandWhat it does
git checkout -b <name>Create and switch to a new branch
>>Append a line to a file
git add -A && git commit -mStage everything and commit

Step 2: watch it run

gh workflow list
gh run list --workflow="IaC Security Scan" --limit 3
CommandWhat it does
gh workflow listLists the repository's workflows
gh run list --workflow=... --limit 3Shows the latest runs of one workflow

You can also open the Actions tab on GitHub.

Step 3: read the scan summary

RUN_ID=$(gh run list --workflow="IaC Security Scan" --limit 1 --json databaseId -q '.[0].databaseId')
gh run view "$RUN_ID" --log | grep -oE "Passed checks: [0-9]+, Failed checks: [0-9]+, Skipped checks: [0-9]+" | sort -u
gh run view "$RUN_ID" --log | grep -oE "FAILED for resource: [^ ]+" | sort -u
PartMeaning
gh run view <id> --logPrint the run's full log
grep -oE "..."Print only the matching part of each line
sort -uSort and remove duplicate lines

Expected: a count of passed and failed checks, and a list of failing resources such as the security group and the public bucket from Phase 1.

Verify

The run finished, and the failing resources match the weaknesses you planted.

Troubleshooting

SymptomLikely causeFix
The workflow does not startChanged files are outside the trigger pathsEdit a file under phase1_vm_mongodb/
The upload step failsCode scanning upload needs GitHub Advanced Security on private repositoriesThe scan result is still in the step log; the pipeline continues
gh: command not foundGitHub CLI not installedInstall it, or use the Actions tab

Clean up

Delete the test branch after the pull request: git push origin --delete test-iac-scan.

Check yourself

  1. Why scan before deploying?
  2. Why is it acceptable here that findings do not fail the run, and when would you change that?
