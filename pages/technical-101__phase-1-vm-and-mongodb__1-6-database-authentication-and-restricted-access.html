1.6 Database authentication and restricted access

Time 15 minutesAWS cost None beyond the running VMNeeds 1.1 completed; the final step needs Phase 2Source script Technical_Exercise/phase1_vm_mongodb/p1demo/121_Restricted_Access_With_Auth.sh

Goal

Show that the database accepts connections only from the Kubernetes network and that it demands a login.

Why it matters

Two controls protect the database, even though it runs an outdated version. A network rule limits who can reach port 27017. Authentication rejects anonymous commands. Checking both end to end is better than reading the configuration alone. The rule says what should happen. The tests show what does happen.

Before you start

Open a terminal in the phase1_vm_mongodb folder and set the variables below. Find the values in the cloud console or with terraform output.

export INSTANCE_ID="<YOUR_INSTANCE_ID>"
export KEY_PATH="./wiz-exercise-key.pem"
IP=$(aws ec2 describe-instances --instance-ids "$INSTANCE_ID" \
  --query 'Reservations[].Instances[].PublicIpAddress' --output text)
VariableMeaning
INSTANCE_IDThe VM's ID, like i-0abc...
KEY_PATHThe private key from lab 1.1
IPThe VM's current public IP, looked up each time because it can change

Also set:

export SG_ID=$(aws ec2 describe-instances --instance-ids "$INSTANCE_ID" \
  --query 'Reservations[].Instances[].SecurityGroups[].GroupId' --output text)
export PRIVATE_IP=$(aws ec2 describe-instances --instance-ids "$INSTANCE_ID" \
  --query 'Reservations[].Instances[].PrivateIpAddress' --output text)
VariableMeaning
SG_IDThe VM's firewall group
PRIVATE_IPThe VM's address inside the private network

Steps

Step 1: read the firewall rule for the database port

aws ec2 describe-security-groups --group-ids "$SG_ID" \
  --query 'SecurityGroups[].IpPermissions[?ToPort==`27017`]'

Expected: the allowed sources are the private subnet ranges where the cluster's nodes will live, not 0.0.0.0/0.

Step 2: try from outside (should fail)

nc -zv -w 3 "$IP" 27017
PartMeaning
ncnetcat, a simple network tool
-zTest only; send no data
-vVerbose output
-w 3Time out after 3 seconds

Expected: a timeout or refusal. This is correct.

Step 3: try a privileged command without logging in (should fail)

ssh -i "$KEY_PATH" -o ConnectTimeout=5 "ubuntu@$IP" \
  "mongo --host $PRIVATE_IP --eval 'db.adminCommand({listDatabases:1})'"
PartMeaning
mongo --hostConnect to the database at that address
--eval '...'Run one command
listDatabasesA privileged command that lists databases

Expected: Unauthorized (error code 13).

Step 4: log in and check your identity

Log in to the VM, then run the shell and let it ask for the password so it never appears in your command history.

ssh -i "$KEY_PATH" "ubuntu@$IP"
mongo --host "$PRIVATE_IP" -u taskyAdmin --authenticationDatabase admin

Then, inside the shell:

db.runCommand({connectionStatus:1})
PartMeaning
-u taskyAdminThe admin user from lab 1.1
--authenticationDatabase adminThe database where that user is defined
connectionStatusShows who the server thinks you are

Expected: authenticatedUsers lists taskyAdmin.

Warning: do not put the password in the command (-p '...'). It would be stored in shell history and visible to other users in the process list.

Step 5: try from the Kubernetes network (after Phase 2)

Once the cluster exists, a throwaway pod should reach the port.

kubectl run nettest --rm -it --restart=Never --image=nicolaka/netshoot -n tasky \
  -- nc -zv "$PRIVATE_IP" 27017
PartMeaning
kubectl run nettestStart a temporary pod named nettest
--rm -itRemove it when done; attach your terminal
--restart=NeverRun once
--image=nicolaka/netshootAn image full of network tools
-n taskyIn the tasky namespace
nc -zv ... 27017Test the port as in Step 2

Expected: the connection succeeds. Skip this step until Phase 2 is done.

Verify

Rule limits sources (1), outside is blocked (2), anonymous access fails (3), authenticated access works (4), and the cluster can reach it (5).

Troubleshooting

SymptomLikely causeFix
Step 3 succeedsAuthentication is offCheck authorization: enabled in the MongoDB config on the VM
Step 4 login failsWrong password or databaseUse the password from your terraform.tfvars and --authenticationDatabase admin
Step 5 times outCluster nodes are not in the allowed rangesCompare the node subnets with the rule in Step 1

Clean up

The throwaway pod removes itself.

Check yourself

  1. Why test from outside and from inside instead of only reading the rule?
  2. Why is a password on the command line a risk?
