1.4 Over-permissive IAM role

Time 15 minutesAWS cost None beyond the running VMNeeds 1.1 completed and the VM runningSource script Technical_Exercise/phase1_vm_mongodb/p1demo/112_Overly_Permissive_CSP_Role.sh

Goal

Show that the VM's cloud role grants far more than it needs, and what an attacker could do with it.

Why it matters

The VM's role carries AmazonEC2FullAccess. That policy gives full control of every EC2 resource in the account. Code on the VM receives that role's credentials automatically, from the instance metadata service. So anyone who gets a shell on the VM inherits the role, with no credential theft needed. This combines with an SSH port open to the internet, from 1.3 SSH exposed to the internet. Together they form a toxic combination: a small weakness becomes an attack path. Inside-out tools such as Mondoo flag over-broad identities. An adversarial test would prove the path is real. See PEM and the four perspectives.

Before you start

Open a terminal in the phase1_vm_mongodb folder and set the variables below. Find the values in the cloud console or with terraform output.

export INSTANCE_ID="<YOUR_INSTANCE_ID>"
export KEY_PATH="./wiz-exercise-key.pem"
IP=$(aws ec2 describe-instances --instance-ids "$INSTANCE_ID" \
  --query 'Reservations[].Instances[].PublicIpAddress' --output text)
VariableMeaning
INSTANCE_IDThe VM's ID, like i-0abc...
KEY_PATHThe private key from lab 1.1
IPThe VM's current public IP, looked up each time because it can change

Also set the role name and region:

export ROLE_NAME="wiz-exercise-mongo-vm-role"
export REGION="us-east-1"

Steps

Step 1: see what the role is allowed to do

aws iam list-attached-role-policies --role-name "$ROLE_NAME"
PartMeaning
aws iamThe identity and access management service
list-attached-role-policiesShow the managed policies attached to a role
--role-nameThe role the VM uses

Expected: a policy named AmazonEC2FullAccess.

Step 2: use the role from inside the VM

The next command runs on the VM and uses no keys of yours. The VM's own role does the work.

ssh -i "$KEY_PATH" -o ConnectTimeout=5 "ubuntu@$IP" \
  "aws ec2 describe-instances --region $REGION \
   --query 'Reservations[].Instances[].{ID:InstanceId,Name:Tags[?Key==\`Name\`].Value|[0]}' \
   --output table"
PartMeaning
ssh ... "<command>"Run one command on the VM and return
aws ec2 describe-instancesList virtual machines (in the whole account, not only this VM)
--region $REGIONThe region to look in
Tags[?Key==\Name\`].Value[0]`Pick each machine's Name tag

Expected (example): a table that lists every VM in the account by name.

Step 3: see the wider blast radius

ssh -i "$KEY_PATH" -o ConnectTimeout=5 "ubuntu@$IP" \
  "aws ec2 describe-security-groups --region $REGION --output table"

This dumps every firewall group in the account, which would help an attacker plan the next step.

Verify

Steps 2 and 3 return data about the whole account, although you supplied no credentials on the VM.

Fix it

Replace the broad policy with the smallest one the VM needs. Here it only writes backups to one bucket (that policy already exists in iam.tf).

aws iam detach-role-policy --role-name "$ROLE_NAME" \
  --policy-arn arn:aws:iam::aws:policy/AmazonEC2FullAccess
PartMeaning
detach-role-policyRemove a managed policy from the role
--policy-arnThe policy to remove
Caution: Terraform still attaches the policy. A later terraform apply puts it back, so the lasting fix is to remove the attachment resource in iam.tf.

Troubleshooting

SymptomLikely causeFix
AccessDenied on list-attached-role-policiesYour lab user lacks IAM readAdd IAM read permission to the lab user
Step 2 prints an errorThe role was already detachedExpected after the fix

Clean up

Nothing to remove. Restoring the policy is done by terraform apply.

Check yourself

  1. Why does code on the VM need no keys to call the cloud?
  2. Which two weaknesses (this lab and 1.3) combine into an attack path?
