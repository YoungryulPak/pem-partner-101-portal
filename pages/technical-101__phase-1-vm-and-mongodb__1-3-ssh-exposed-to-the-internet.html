1.3 SSH exposed to the internet

Time 10 minutesAWS cost None beyond the running VMNeeds 1.1 completed and the VM runningSource script Technical_Exercise/phase1_vm_mongodb/p1demo (SSH check)

Goal

Prove that the VM accepts SSH connections from anywhere, by reading the firewall rule and then logging in.

Why it matters

An SSH port open to 0.0.0.0/0 lets anyone on the internet attempt to log in. It is one of the most common findings in cloud-posture tools, and it is the kind of exposure an outside-in scan reports without any access to your account.

Reading the rule is only a finding. Logging in shows the exposure is real. It moves from "configured badly" to "reachable and usable". That is the difference between assessing and validating in the PEM lifecycle. See Validate.

Before you start

Open a terminal in the phase1_vm_mongodb folder and set three variables. Find the values in the AWS console or with terraform output.

export INSTANCE_ID="<YOUR_INSTANCE_ID>"
export KEY_PATH="./wiz-exercise-key.pem"
VariableMeaning
INSTANCE_IDThe VM's ID, like i-0abc...
KEY_PATHPath to the private key from lab 1.1

Steps

Step 1: find the VM's security group

SG_ID=$(aws ec2 describe-instances --instance-ids "$INSTANCE_ID" \
  --query 'Reservations[].Instances[].SecurityGroups[].GroupId' --output text)
echo "$SG_ID"
PartMeaning
SG_ID=$(...)Run the inner command and store its output in SG_ID
describe-instances --instance-idsLook up this VM
--query 'Reservations[].Instances[].SecurityGroups[].GroupId'Walk down the JSON to the security group ID
--output textPlain text so the variable holds only the ID

Expected (example): sg-0123456789abcdef0

Step 2: read the port 22 rule

aws ec2 describe-security-groups --group-ids "$SG_ID" \
  --query 'SecurityGroups[].IpPermissions[?ToPort==`22`]'
PartMeaning
describe-security-groupsShow firewall groups
--group-ids "$SG_ID"Only this one
IpPermissions[?ToPort==\22\]Inbound rules, filtered to those for port 22. The backticks mark a number in JMESPath

Expected (example): the output contains "CidrIp": "0.0.0.0/0". That value means every address on the internet.

Step 3: find the VM's current public IP

IP=$(aws ec2 describe-instances --instance-ids "$INSTANCE_ID" \
  --query 'Reservations[].Instances[].PublicIpAddress' --output text)
echo "Public IP: $IP"

The public IP can change if the VM restarts, so look it up each time instead of copying an old one.

Step 4: check the port is reachable

nc -zv -w 3 "$IP" 22
PartMeaning
ncnetcat, a simple network tool
-zOnly test the connection; send no data
-vVerbose: print the result
-w 3Give up after 3 seconds
"$IP" 22Target address and port

Expected: Connection to <IP> port 22 [tcp/ssh] succeeded!

Step 5: log in

ssh -i "$KEY_PATH" -o ConnectTimeout=5 "ubuntu@$IP" 'whoami; hostname; uptime'
PartMeaning
-i "$KEY_PATH"Use your private key
-o ConnectTimeout=5Fail after 5 seconds instead of hanging
"ubuntu@$IP"User and address
'whoami; hostname; uptime'Commands to run on the VM, then disconnect

Expected (example): ubuntu, the VM's hostname, and its uptime. This proves an authenticated shell, not just an open port.

Verify

Steps 2, 4 and 5 all agree: the rule allows 0.0.0.0/0, the port answers, and login works.

Fix it (optional, recommended)

Replace the open rule with one for your own address only.

MYIP=$(curl -s https://checkip.amazonaws.com)
aws ec2 revoke-security-group-ingress --group-id "$SG_ID" --protocol tcp --port 22 --cidr 0.0.0.0/0
aws ec2 authorize-security-group-ingress --group-id "$SG_ID" --protocol tcp --port 22 --cidr "$MYIP/32"
PartMeaning
curl -s https://checkip.amazonaws.comAsk AWS what your public IP is; -s hides progress
revoke-security-group-ingressRemove an inbound rule
authorize-security-group-ingressAdd an inbound rule
--cidr "$MYIP/32"Exactly one address (/32)
Caution: Terraform still has the old rule in code. If you run terraform apply again it will put the open rule back, which is why real fixes go through the code. Later labs and Phase 3 show that workflow.

Troubleshooting

SymptomLikely causeFix
Connection timed outVM stopped, wrong IP, or your network blocks 22Re-run Step 3; check the VM is running
Permission denied (publickey)Wrong key or userUse the key from 1.1 and user ubuntu
Permissions are too openKey file modechmod 400 on the key
nc: command not foundnetcat missingInstall it, or skip to Step 5

Clean up

Nothing to remove for the checks. If you did the fix, you changed the rule outside Terraform; terraform destroy later removes it anyway.

Check yourself

  1. What does 0.0.0.0/0 mean in a firewall rule?
  2. Why is a successful login stronger evidence than reading the rule?
  3. Which perspective in PEM and the four perspectives would report this port without access to your account?
