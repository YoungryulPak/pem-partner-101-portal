4.8 Audit logs: CloudTrail and EKS

Time 20 minutesAWS cost Small CloudWatch Logs storage costNeeds Phase 2 cluster runningSource script Technical_Exercise/phase4_ai_cnapp_incident/incident_response/detect_findings.sh (detection queries only)

Goal

Turn on the cluster's audit log and learn the query that would show a service account reaching beyond its own namespace.

Why it matters

A cloud account logs management actions by default, through CloudTrail. A Kubernetes cluster's own audit log is not on by default, though. Without it, there is no record of what happened inside the cluster API. That record would show who did what, from which identity, to which object. This lab turns detection into something you can actually query. Querying logs is the CDR half of CNAPP: detection and response.

This page covers enabling and querying logs only. It does not include steps that act inside the cluster using another identity's credentials. Keep any such test to your own lab. Run it only under your own authorization, and only on resources you own.

Steps

Step 1: turn on EKS control-plane logging

aws eks update-cluster-config \
  --name wiz-exercise-eks \
  --region us-east-1 \
  --logging '{"clusterLogging":[{"types":["audit","authenticator"],"enabled":true}]}'
PartMeaning
update-cluster-config --loggingTurns on specific control-plane log types
"audit"Every request made to the Kubernetes API, with the identity that made it
"authenticator"Records of identity checks

Step 2: wait for the update to finish

aws eks describe-update --name wiz-exercise-eks --region us-east-1 --update-id <UPDATE_ID>

The update ID is in the output of Step 1. Repeat until status is Successful.

Step 3: confirm the log group exists

aws logs describe-log-groups --region us-east-1 \
  --log-group-name-prefix /aws/eks/wiz-exercise-eks/cluster \
  --query 'logGroups[].logGroupName' --output text

Expected: /aws/eks/wiz-exercise-eks/cluster.

Step 4: query for cross-namespace access by a service account

This is the query you would run after any suspected incident, to see whether a given identity reached outside its own namespace.

aws logs start-query --region us-east-1 \
  --log-group-name "/aws/eks/wiz-exercise-eks/cluster" \
  --start-time "$(date -v-1H +%s 2>/dev/null || date -d '1 hour ago' +%s)" \
  --end-time "$(date +%s)" \
  --query-string 'fields @timestamp, user.username, verb, objectRef.namespace, objectRef.resource
| filter user.username like /tasky-sa/
| filter objectRef.namespace != "tasky"
| sort @timestamp desc
| limit 50' \
  --query 'queryId' --output text

Then, a few seconds later:

aws logs get-query-results --region us-east-1 --query-id <QUERY_ID> --output table
PartMeaning
start-query / get-query-resultsRun a CloudWatch Logs Insights query and fetch its result
filter user.username like /tasky-sa/Keep only events from this identity
filter objectRef.namespace != "tasky"Keep only events outside the identity's own namespace

Reading the result: any row is a signal worth investigating: an identity that normally stays in one namespace reached another one. This is exactly the kind of signal 2.6 cluster-admin role binding warns about, and the kind of pattern an inside-out platform would alert on.

Verify

The log group exists and the query returns a result set (it may be empty if the identity has not made any cross-namespace calls).

Troubleshooting

SymptomLikely causeFix
Log group not foundStep 1 has not finishedRe-check with describe-update
Query returns nothingNo matching activity in the time windowWiden the time window

Clean up

Audit logging can be turned off the same way, with "enabled": false, to avoid ongoing log storage cost.

Check yourself

  1. Why is a cluster's own audit log not on by default?
  2. What does it mean if this query returns a row for tasky-sa?
