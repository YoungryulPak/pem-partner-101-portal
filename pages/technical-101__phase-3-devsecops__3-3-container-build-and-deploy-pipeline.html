3.3 Container build and deploy pipeline

Time 30 minutesAWS cost None beyond the running clusterNeeds 3.1 completed; Phase 2 cluster runningSource script Technical_Exercise/phase3_devsecops/.github/workflows/build-and-deploy.yml; github_oidc.tf

Goal

Build the application image. Scan it. Push it to the registry. Roll it out to the cluster automatically. Do all of this with no stored cloud keys.

Why it matters

A pipeline that deploys needs permission to the cloud. The weak way is a long-lived access key, stored as a secret. The better way is OIDC. GitHub proves who the job is. The cloud then hands out a short-lived role, only to that one repository. There is no key to leak, and nothing to rotate.

How the pipeline is built

StepWhat it does
TriggerA push to main that changes tasky-main/, or a manual run
Configure cloud credentialsAssumes the lab role through OIDC
Log in to the registryShort-lived registry login
Builddocker buildx build --platform linux/amd64, matching the node CPU
Scan with TrivyLooks for Critical and High vulnerabilities in the image; results go to the Security tab; soft-fail
Tag and pushPushes the image with the commit ID as tag and as latest
Update kubeconfig and deployConnects to the cluster and rolls out the new image

The base images (alpine:3.17.0, golang:1.19) are old on purpose, so many findings are expected.

Steps

Step 1: create the OIDC trust with Terraform

The file github_oidc.tf sits in phase2_k8s_tasky/terraform so it shares the cluster's state. Tell it which repository may deploy:

cd phase2_k8s_tasky/terraform
cat > terraform.tfvars << 'EOF'
github_repo = "<YOUR_ACCOUNT>/<YOUR_REPO>"
EOF
terraform init
terraform plan
PartMeaning
cat > file << 'EOF' ... EOFWrite the lines between the markers into the file
github_repoOnly this repository may assume the role

Expected in the plan: an OIDC provider for GitHub, a role for GitHub Actions and an EKS access entry for that role. Then:

terraform apply
terraform output github_actions_role_arn

Step 2: give the role's ARN to GitHub

On GitHub: repository Settings > Secrets and variables > Actions > New repository secret. Name: AWS_GITHUB_ACTIONS_ROLE_ARN. Value: the ARN printed above.

An ARN is not a password, but keeping it as a secret is a good habit.

Step 3: run the pipeline

Change any file in tasky-main/ and merge to main, or start it by hand:

gh workflow run "Build, Scan, and Deploy Tasky"
gh run watch
CommandWhat it does
gh workflow run "<name>"Starts a workflow manually
gh run watchFollows the run live

Step 4: confirm the new image is running

kubectl rollout status deployment/tasky -n tasky
kubectl get pods -n tasky
CommandWhat it does
kubectl rollout statusWaits until the update finishes
kubectl get pods -n taskyLists the pods

Expected: a new pod created recently, in Running state.

Step 5: read the Trivy findings

On GitHub: Security > Code scanning, or from the CLI:

gh api "repos/<YOUR_ACCOUNT>/<YOUR_REPO>/code-scanning/alerts"   --jq '.[] | "\(.tool.name)  \(.rule.severity // "n/a")  \(.state)"' | sort | uniq -c | sort -rn

Verify

The run succeeded, the image tagged with the commit ID is in the registry, and a new pod is running.

Troubleshooting

SymptomLikely causeFix
Could not assume roleWrong repository in github_repo, or the secret is missingCheck both values
Deploy step cannot reach the clusterThe role has no cluster accessConfirm the EKS access entry was created
Trivy upload failsCode scanning needs Advanced Security on private repositoriesThe scan still ran; the rest continues

Clean up

Delete the OIDC provider and role with the rest of Phase 2 (see 2.9 Destroy in the right order).

Check yourself

  1. Why is OIDC safer than a stored access key?
  2. What would you change to make the Trivy scan block a deployment?
