1.7 Daily backup to object storage

Time 15 minutesAWS cost Small storage costNeeds 1.1 completed and the VM runningSource script Technical_Exercise/phase1_vm_mongodb/p1demo/130_Daily_MongoDB_Backup.sh; s3.tf

Goal

See the scheduled job that backs up the database every day to object storage, and confirm the backups arrive.

Why it matters

Backups protect against data loss. But a backup holds the same sensitive data as the database itself. Where the backup is stored, and who can read it, matter as much as the schedule does. The next lab, 1.8 Public bucket: read and list, shows what happens when the bucket is public.

Before you start

Open a terminal in the phase1_vm_mongodb folder and set the variables below. Find the values in the cloud console or with terraform output.

export INSTANCE_ID="<YOUR_INSTANCE_ID>"
export KEY_PATH="./wiz-exercise-key.pem"
IP=$(aws ec2 describe-instances --instance-ids "$INSTANCE_ID" \
  --query 'Reservations[].Instances[].PublicIpAddress' --output text)
VariableMeaning
INSTANCE_IDThe VM's ID, like i-0abc...
KEY_PATHThe private key from lab 1.1
IPThe VM's current public IP, looked up each time because it can change

Also set the bucket name (see terraform output):

export BUCKET="<YOUR_BACKUP_BUCKET>"

Steps

Step 1: read the schedule

ssh -i "$KEY_PATH" -o ConnectTimeout=5 "ubuntu@$IP" 'cat /etc/cron.d/mongo-backup'
PartMeaning
/etc/cron.d/System cron job definitions
catPrint the file

Expected (example): a line like 0 3 * root /usr/local/bin/mongo_backup.sh. The five fields mean minute 0, hour 3, every day, every month, every weekday; it runs as root, so 03:00 UTC daily.

Step 2: run the backup once now

Do not wait for 03:00.

ssh -i "$KEY_PATH" "ubuntu@$IP" 'sudo /usr/local/bin/mongo_backup.sh'
PartMeaning
sudoRun as root, like the cron job
/usr/local/bin/mongo_backup.shThe backup script installed on the VM

Step 3: confirm the object arrived

aws s3 ls "s3://$BUCKET"
PartMeaning
aws s3 lsList objects in a bucket
s3://$BUCKETThe backup bucket

Expected: at least one backup object with a timestamp.

Verify

The schedule exists, the manual run succeeded and the object is in the bucket.

Troubleshooting

SymptomLikely causeFix
Step 2 reports an access error to the bucketThe VM role cannot writeCheck the backup policy in iam.tf (and see 1.4 Over-permissive IAM role)
Bucket is emptyThe script failedRun it again and read its output

Clean up

Delete test backups when you finish, as part of Cost, safety and cleanup; terraform destroy removes the bucket if it is empty.

Check yourself

  1. What does 0 3 * mean?
  2. Who can read the backup, and should they be able to?
